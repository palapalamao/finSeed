# FIN Energy API Contract for 0.16.0

## FIN Energy 0.16.0 native licensing and namespace upgrade

The current technical namespace is `finEnergy`: Pod `finEnergy.pod`, `FinEnergy*` types, `finEnergy*` Axon entry points and `/api/{project}/ext/finEnergy/v1`. Product tags use `finEnergy*`; FIN standard tags retain their standard semantics. The 0.14.37 records cited below remain historical evidence, not 0.16.0 runtime acceptance.

`GET license/status` returns a read-only native status object: `source:"fin"`, `status:"active"|"missingFeature"|"invalid"|"inactive"`, `feature`, `canManageFinLicense`, optional administrator `hostId`, and an optional reason. The current proposed feature token is `fin energy`; HQ confirmation and a genuine FIN grant are release requirements. There are no legacy application license import/delete/request routes or meter quotas in the native candidate. FIN can deactivate the entire extension, so the status route itself is not guaranteed when the native feature is missing.

Administrator-only namespace functions are `finEnergyRenameNamespace("enerCubix","finEnergy",false)` for preview, the same call with `true` and the exact returned revision for apply, `finEnergyResumeNamespace(backup)` for the same journal, and `finEnergyRollbackNamespace(backup)` for guarded rollback. Preview does not publish changes. Folio records, native alarms and owned images are separately backed up and journaled; IDs and primary histories are retained. The revision binds the migration delta; a separate digest binds full recovery snapshots. Current collection values and acknowledgements are preserved. Keep business jobs and configuration changes paused throughout maintenance until the original journal is complete or rolled back. Refer to the upgrade guide for limitations and exact sequencing.

`409` also includes `LICENSE_REQUIRED` for an unavailable native energy feature and `NAMESPACE_MIGRATION_REQUIRED` for legacy project upgrade. These are application prerequisites, not ordinary partial-module errors. A prior snapshot must not be presented as a successful new query.

FIN Framework 5.3.0.2761. Browser calls use the same-origin project endpoint `/api/{project}/ext/finEnergy/v1` and the authenticated FIN session. Use `finCsrfFetch` from `haystack-nclient` for JSON calls. FIN supplies the current user, project and access controls.

POST accepts a JSON object with `Content-Type: application/json`. `report`, `cockpit` and `cleaning/preview` are read-only POST routes. All other POST routes require an administrator. Migration preview requires an administrator on both the GET and POST routes. Mutations require the current `mod` where specified.

The normal response is `{ok:true,data:...}` with HTTP 200. Application errors use `{ok:false,error:{code,msg}}` with a non-2xx status. The image route returns binary content on success. FIN can reject expired sessions or CSRF before FIN Energy dispatches the request. Clients also handle FIN redirects and non-JSON errors. JSON and cockpit images use `Cache-Control: no-store`. Standard POST bodies permit up to 2,097,152 characters. Asset upload permits up to 3,145,728 UTF-8 bytes of JSON.

## Current data-source and version boundary

Since 0.12.9, every measured, physical or virtual device reads energy exclusively from its explicitly configured primary point's native FIN history. FIN owns collection and history storage; FIN Energy reads, cleans, calculates and presents results without a second time-series fact store. A missing primary or missing primary history stays missing: auxiliary histories, old minute batches, current child sums and formula-input histories are never substitutes for that device's own history. Contribution members independently read their own primaries.

Queries use current configured relationships. The same deduplicated meter set, range, cutoff, metric/unit and cleaning configuration must produce the same base-use result across views and reports. A successful report/export snapshot remains frozen when draft controls change. Query-time cleaning never rewrites stored history; missing, NA, real zero and estimated quality remain distinct.

Cost energy-flow scope totals use the same selected primary-meter frontier as the other cost reports, in both relations and end-use modes. `extra.energyFlowAccounting.basis:"meterCostScope"`, `memberIds`, `unionValue` and `unionQuality` identify this deduplicated available cost. Contribution members and shared references describe the individual graphs only; they neither replace the selected meters' own primary histories nor add their cost a second time. Energy flow retains its existing physical/contribution accounting. Missing primary histories remain missing, including for virtual total meters.

`FinEnergyMeterGeneration.update/ensure` are inert; `publish/recalculate` reject calls. `tasks` accepts only `scanAlarms` and `setAlarmEnabled`; `recalculate` and `setCalculationEnabled` return validation errors. Retiring generation does not authorize deleting, trashing, rebinding or migrating existing records. Current-value auto-sum remains separate from historical reporting and writes no history.

Package versions come from `build.fan` and the package manifests. From 0.12.12, the frontend identifies its own compiled version, detects a different backend version and offers a localized reload; the versioned HTML entry avoids silently reusing an older UI. Implementation, local validation, integration and deployment are separate evidence levels. Sections explicitly labeled historical below describe retired behavior, not current API promises.

## Cockpit snapshot

POST `cockpit` is a read-only authenticated operation, using the same native FIN session and CSRF route as `report`. It is not a configuration save and does not scan or acknowledge alarms. The packaged native application entry opens the versioned `#/cockpit?project=...`; `#/dashboard` retains the previous overview. The frontend capability switch can fall back to the previous overview.

Request shape (schema version 1):

```json
{
  "schemaVersion": 1,
  "requestId": "client-sequence",
  "reportScope": {"dimension": "space", "nodeIds": ["native-space-ref"], "selectionIntent": "range"},
  "focusCategoryId": "energy-category-ref",
  "time": {"preset": "thisMonth", "period": "day"},
  "comparison": {"mode": "presetDefault"},
  "modules": ["kpis", "space", "trend", "time", "endUse", "organization", "balance", "efficiency", "issues"]
}
```

`dimension` accepts space/metering/organization. `selectionIntent` is range or explicitObjects. A focus object is client observation state. `time.preset` accepts today/thisMonth/thisYear/custom, with absolute `from/to` for custom. A new request can omit `asOf` and use the FIN server cutoff. The returned snapshot freezes that cutoff. Comparison modes are `none`, `presetDefault`, `previousMonth` and `custom`. Default comparison uses the same local cutoff on the previous day for today, the previous year for month/year, and no reference for custom. `previousMonth` applies to `thisMonth` and `custom`. It shifts both boundaries back one calendar month in the project timezone and clamps a missing day to the end of the month. `custom` comparison requires explicit reference `from/to`. Returned ranges disclose month-day, leap-day, DST and duration adjustments. Change rates require comparable data and a nonzero reference.

A request requires a nonempty `requestId` of at most 200 characters, 1–200 `reportScope.nodeIds`, a `focusCategoryId` and a nonempty `modules` list. Optional `auxiliaryCategoryId` must differ from the focus category. Cockpit periods are `hour`, `day` and `month`. Project and timezone come from the FIN context. Use ISO 8601 with an explicit offset for absolute times. The server caps a future `asOf` at its current time.

The response contains `schemaVersion/snapshotId/requestId/generatedAt/context/provenance/boundary/modules/reports/quality/capabilities/limitations`. Context includes the project timezone and absolute current/reference intervals. Provenance includes current configuration Ref/mod fingerprint, own-primary history basis, actual read-observation interval, applied cleaning snapshots, source-last-observed time and any streaming limits. `sourceLastObservedAt` is an observation, never proof that history is complete up to that instant. A new query at the same asOf can see late source history or newer configuration; snapshots are not historical MVCC.

`boundary.meterIds/sourcePointIds` identify the effective energy boundary. Different views of the same set/configuration/range reuse the same base-use result. Explicit overlapping objects keep their own details but do not expose a mixed scalar or invented shares. Energy always comes from each device's explicitly configured primary history, including virtual devices; contributions never substitute for missing own history.

Each optional module has `status:ok|partial|empty|unavailable|error`, data and reasonCodes. Missing optional configuration or an ordinary isolated module failure does not erase other successful results. Invalid input, authorization failures and request resource failures remain whole-request errors. Report references resolve to existing ReportResult objects in the same package:

| Module | Frozen data |
| --- | --- |
| kpis | Four cards, strict/available values, quality, comparison and controlled management conclusions; carbon falls back to current ongoing events when its coefficient is missing |
| space | Accessible native space hierarchy, node evidence and the resolved energy boundary |
| trend | Main energy profile reportRef |
| time | Hour-of-day mean energy reportRef, complete-local-day heatmap, excluded incomplete days and only configured working-calendar reports |
| endUse | Utility reportRef, effective meter IDs and additive flag. Uses the cockpit's resolved meter boundary. Unassigned use remains separate. |
| organization | Current hierarchy, root IDs and unassigned bucket; parent and child levels are not added together |
| balance | Existing energy-flow reportRef and independent graph IDs; original graph/accounting/shared-source contracts apply |
| efficiency | Applicable COP config Ref/mod, numerator, denominator, ratio, service boundary and reportRef; total output/total input, never a mean of interval ratios |
| issues | One current event observation, stable episode/native alarm identity, acknowledgement and recovery separately, read-only hourly evidence and actual metric quality issues |

Current native event observation is separate from historical asOf. Selected objects and effective statistical meters define event scope; selecting a measured total does not imply all descendant events. An acknowledged but unrecovered episode remains ongoing. Event evidence may precede the parent's energy interval; opening it uses a separate absolute request and preserves the parent snapshot. Message-center eventId links locate an existing episode without scanning or acknowledgement. No guessed native deep-link or new alarm/message store is introduced.

### Snapshot transport and resource guards

By default the JSON envelope contains the logical snapshot directly in `data`. With `payloadEncoding:"compact-v1"`, `data` contains `{payloadEncoding:"compact-v1",codecVersion:1,snapshot,evidence}`. The bundled client negotiates this encoding and decodes it before drawing charts or exporting. Evidence references and tabular packing share wire representations. In compact mode the server also projects bounded diagnostics into `diagnostics` with `rowBudget`, `returnedCount`, truncation and per-entry provenance. Distinguish omitted detail from missing usage. The business values and aggregate coverage retain their original meaning. Clients can omit the codec field to receive plain JSON. See [cockpitTypes.ts](../finEnergy.pod/ts/src/cockpitTypes.ts) and [cockpitPayload.ts](../finEnergy.pod/ts/src/cockpitPayload.ts).

Cockpit history reads use request-local prepared summaries over bounded native chunks. Current guards allow up to 200 selected scope IDs and effective devices, two energy categories, 20 applicable COP configurations and 366 local days in the selected interval, with a separately resolved comparison range. The raw adapter targets 50,000 samples per block, permits up to 200,000 held raw samples and 20 million scanned samples. A separate 200,000-entry budget covers prepared and temporary structures. The execution deadline is 30 seconds and the soft observation target is 20 seconds. The serialized HTTP response cap is 8 MiB. Admission allows one active request per user/project and two per project. The server assembles and validates the response before sending it. A resource failure produces an explicit error. Standalone `report` keeps its own history sample guard.

Budget and rule scopes use `scopeKind:"project"|"space"` with the project Ref or a permitted native Site/Floor Ref. Budget month is `YYYY-MM`, currency is a three-letter uppercase code and amount is positive. Use `distribution:"uniform"` for equal daily allocation or `"daily"` with one nonnegative amount per calendar day whose sum matches the monthly amount. Budget eligibility requires matching boundary, category, month and currency. Partial days use actual local day duration including DST. The snapshot keeps `periodBudget`, `monthBudget`, `periodActualCost` and budget basis. Formal `variancePct` and `monthUsagePct` require eligible cost coverage. Available-only cost can populate `referenceVariancePct` and `referenceMonthUsagePct` with explicit `referenceBasis`.

A rule is `nonWorkingHighUsage` with a calendar Ref and compatible usage unit, or `budgetVariance` with a currency and `%` threshold unit. Thresholds are finite nonnegative values. Evaluation provides evidence and reasons in the snapshot. A budget rule uses the formal variance. Rule clues and native FIN alarms have separate types.

All asset mutations return the updated asset catalog. Writes check `manifestMod` and, for existing item edits, `mod`. Assets support PNG/JPEG, with a 2 MiB image size cap, at most 4,096 pixels per side and 8 million total pixels. Each project supports up to 10 assets and each asset up to 100 Site/Floor hotspots. Binary download uses the catalog content hash and FIN permissions. The server resolves the filename from asset metadata in private project storage.

## Native equipment storage (0.4.0)

All normal meter/sensor saves, including batch assignment and role changes, write FIN's existing equipment record. Its ID is the physical equipment ID; `nativeEquip:true` and a model marker are not required to choose this storage path. Parent references point to upstream equipment IDs, and every equipment business scalar/reference is stored as a visible `finEnergy*` tag on that same record. Normal saves never create an independent meter archive. Editing retained historical archives first repairs their native equipment configuration with validated references, optimistic revisions and recovery snapshots; no user migration workflow is required. Shared tariffs, calendars, expressions and other project configuration retain their own records.

Meter `autoSum?:boolean` opts into a current cumulative reading on its existing primary `pointId`, advanced by direct-child increments after their individual baselines. An expression-bound virtual device evaluates its configured formula from current inputs for its own eligible point. Adding, removing or rebinding a source never imports its previous lifetime counter. Project `settings.meterRollupSeconds` controls this current-value interval (integer 1–3600 seconds, default 1 when absent). Housekeeping remains serialized. Collected sources cannot be overwritten. This path writes transient current values and continuity state, not point history or minute archives. Report queries always read the selected device's own primary history. The Other settings page preserves unrelated settings and the optimistic `mod` revision.

`catalog.storageModel` is `nativeEquip` for normal operation. Physical meter/sensor `id` and report `nodeIds` are FIN equipment IDs; `pointId` and report `sourceIds` remain native history point IDs. Three views use the same equipment record. `finEnergyAlias` preserves the short name without changing native `dis`/`navName`. The default visible label comes from native equipment. Set `useAlias:true` to display a nonempty configured alias. References use the existing `finEnergy*Ref` tags on equipment; scalar properties use `FinEnergyNativeEquip.scalars` (`finEnergyArea`, `finEnergyMaximum`, `finEnergyHistoryMode`, `finEnergyIncludeInTotals`, etc.). The older archive description below documents retained compatibility data only.

Enrollment writes an existing equipment ID plus its observed `mod`, kind, category and explicit own historized compatible `pointId`. Batch saves are atomic and reject multiple records for one equipment. `tree/manage copy` requires `targetId`, `targetMod`, and the target equipment's `pointId`; it creates no physical archive. `records/delete` and `tree/manage delete` unenroll equipment by removing owned energy tags, preserving equipment, native hierarchy, points and histories. Native virtual equipment is created with `createVirtual:true`, `expressionId`, `siteId`, and a `floorId` belonging to that site; it is excluded from totals by default.

Ordinary meter creation uses `createNative:true`, `kind:'totalMeter'|'meter'`, `name`, `categoryId`, `siteId`, and a `floorId` belonging to that site. It requires no expression and binds no existing point. One atomic commit creates native equipment and its own Number point with matching site/floor references, the category unit (or a compatible selected unit), `his`, `hisTotalized`, site/project timezone and a 15-minute history collection interval. `finEnergyPointRef` targets that new point. Main meters default to `autoSum:true` and `includeInTotals:true`; no current reading or history samples are fabricated. The ordinary-meter entry and expression-device entry are separate; the latter visibly requires expression selection.

Native navigation supplies `nativeTreeParentId`; edits to existing equipment never write FIN location references. `spaceId` means coverage, inferred from installation location when absent. Invalid native tag types, point ownership, history, energy, references and topology appear as `configurationError` and produce `invalidConfiguration` quality instead of an energy value. Refresh reads native edits directly.

`migration/preview` now previews `target:nativeEquip`: old IDs, native IDs, primary points, upstream equipment, per-tag `tagChanges`, conflicts, configuration `revision`, and relevant-source `sourceRevision`. Apply checks both revisions and atomically writes owned tags, dependency rewrites, compatibility aliases, recovery snapshots, and the reading mode. Old physical archives are ignored after apply. `migration {action:finalize,jobId,mod}` removes those archives only after report verification; `rollback` restores old IDs/read mode and only migration-owned changes, stopping on conflicting later edits. Historical alarm source records remain immutable; old report IDs resolve via the compatibility aliases. Use `target:threeTree` only for the previous migration protocol.

## Configuration

`FinEnergyRecord` is an ordinary JSON object: `id?:string,mod?:string,kind:string,name:string` plus the fields below. IDs are FIN ref strings without `@`; stored relationship fields are native Folio Refs. Device properties use visible scalar/reference tags on the original equipment as described above. Shared project configuration uses its own Folio records and `finEnergyConfig` JSON, not files or browser storage. Kind is one of space,organization,group,meter,totalMeter,sensor,category,subcategory,utility,tariff,calendar,expression,cop,template,settings,binding,job,alarm,cleaningProfile.

- space/organization: parentId?,area?,description?. A space can have only a space parent; an organization can have only an organization parent. Their hierarchies are independent of legacy groups and meter topology.
- group: parentId?,area?,description?,alarmLimits:[{categoryId,limit,enabled}]
- meter/totalMeter/sensor: parentId?,spaceId?,meterParentId?,organizationId?,canonicalId?,pointId?,categoryId?,subcategoryId?,utilityId?,tariffId?,expressionId?,area?,maximum?,includeInTotals?,actualEfficiency?,baselineEfficiency?,alarmEnabled?,alarmLimit?,unit?,description?,location?. Meter/totalMeter `historyMode?:auto|cumulative|interval` explicitly interprets legacy histories inside FIN Energy without modifying FIN source tags or samples; explicit modes for the same point must agree. Unspecified mode preserves FIN configuration, including a standalone `hisTotalized` counter marker.
- category: unit; subcategory: categoryId,coalFactor,co2Factor,rawcoalFactor?,oilFactor?; utility: categoryId. Factors are output mass per category energy unit: coal in kgce, CO2 in kgCO2, raw coal/oil in kg. For example 0.1229 kgce/kWh yields 29.496 kgce for 240 kWh.
- tariff: categoryId?,isDefault?,mode=flat|absolute|weekly|monthlyBlock|yearlyBlock,rate:number,rules:[{from?,to?,startHour?,endHour?,weekday?,rate}],exceptions:[{from,to,startHour?,endHour?,rate}],blocks:[{limit:number|null,rate:number}]
- calendar: isDefault?,peakHours:number[],valleyHours:number[],workHours:number[],workDays:number[] (ISO 1 Monday..7 Sunday),exceptions:[{date:string,working:boolean}]
- expression: formula:string,variables:{[variableName]:meterRecordId}
- cop: numeratorId,denominatorId
- template: request:ReportRequest,preset?:thisWeek|lastWeek|thisMonth|lastMonth|thisYear|lastYear
- settings: visibleMetrics:string[],visibleCategoryIds?:string[],rotationSeconds:number. `visibleCategoryIds` selects the energy-category dashboard slides; omission selects all categories, while `[]` selects none. Cost/coal/CO2 slides are selected independently by `visibleMetrics`.
- binding: pointId,role=energy|reference|runtime,alias?
- job: action,enabled,status,from?,to?,message?,processed?,lastRun?
- alarm: nodeId,categoryId?,ts,value,limit,state=open|acknowledged,ackBy?,ackAt?,ackNote?

Meter relationships have distinct meanings: `spaceId` is coverage, `meterParentId` is the confirmed upstream meter, and `organizationId` is accounting ownership. Their native tags are `finEnergySpaceRef`, `finEnergyMeterParentRef`, and `finEnergyOrganizationRef`. `canonicalId` / `finEnergyCanonicalRef` identifies an existing compatibility alias for the same point/expression and energy category; it references a canonical meter/sensor rather than another alias. Upstream meters must also be canonical and in the same energy category. Cycles and missing or incompatible targets are rejected. A physical point has one canonical meter record in the new dimensions; existing duplicate records can remain as legacy aliases. `parentId` / `finEnergyParentRef` on a meter continues to describe only its legacy group and does not imply any of the three new relationships.

GET `catalog` returns `{version,project,projectRef,cockpitConfigRefs,user:{name,canWrite},storageModel:'nativeEquip',spaceSource:'fin',nativeTreePath,nativeTreeWarnings:string[],records:FinEnergyRecord[]}`. `cockpitConfigRefs` lists readable valid cockpit budget and rule revisions as `{id,mod}`. Each request reads the current native `legacy::NavTree.find(cx,"equip")`, preserving navigation names, ordering, nested equipment, point leaves and FIN access checks. There is no persistent mirror or synchronization write on a GET. Page refresh and workspace refresh fetch this projection again.

Native containers project as `kind:'space',nativeReadonly:true,nativeSourceId,nativeSourceKind,parentId`. IDs are native FIN Refs; an existing FIN Energy space with matching `migrationSourceId` keeps its ID. Point leaves use `kind:'nativePoint',nativeReadonly:true,nativeSourceId,parentId,nativeDis,unit?,his?,pointKind?`; these are browsing metadata, never energy archives or implicit history dependencies. The UI displays only point leaves with his:true, as confirmed by the user; all native containers remain. A bound eligible leaf displays its canonical metering configuration under the original FIN leaf name. Historical manual spaces remain in the catalog with `nativeHidden:true` and are omitted from the current FIN tree.

Projected meter records add transient `nativeSpaceReadonly:true,nativeSpaceId?` from the current point parent. Missing/inaccessible sources retain the meter configuration with `nativeSourceMissing:true` and no live coverage. Refresh preserves stored records and organization/upstream references. New/changed bindings persist the native parent as a Folio `finEnergySpaceRef`; unrelated edits retain stored `spaceId` for historical requests. All `native*` fields are stripped before persistence. Native containers and leaves reject structural edits, moves, copies and deletion; Site/Floor area has the explicit area-only exception documented below. Unbound and virtual meter configurations remain in the all-object list and other dimensions.
GET `tree?dimension=space|metering|organization|legacy` returns `{dimension,spaceSource,records:FinEnergyRecord[]}`. The default is `space`, with `spaceSource:'fin'`. Other dimensions return a null `spaceSource`. The response is a flat directory: space/organization entities use same-kind `parentId`, and meters use the relationship appropriate to the requested dimension. New dimensions expose canonical meters; `legacy` includes original groups and compatibility aliases.
GET `points?q=&offset=0&limit=200` -> `{items:FinPoint[],total,offset,limit}` where FinPoint `{id,name,unit,kind,his:boolean,hisMode?,source?,hisStart?,hisEnd?,curStatus?,hisStatus?,hisErr?,hisLastCollect?,navName?,equipId?,equipName?,equipNavName?,floorId?,floorName?,siteId?,siteName?,energyTags?:string[]}`. The HTTP limit is 1–500, with a default of 200. Related labels and IDs come from readable native references. `energyTags` contains native markers.
POST `records` body `{record:FinEnergyRecord}` -> saved FinEnergyRecord; update requires current mod.

Native Site/Floor area uses the restricted payload `{record:{id,mod,kind:'space',areaOnly:true,area:number|null}}`. Only these fields are accepted. Admin and native record read/write access are required. A positive finite number is stored as the original FIN record's `area` Number in m²; null clears it. No name, parent, point, history or secondary space configuration is written. FIN area (including absence) overrides old overlay area; compatible native area units are converted to m² on read.

Meters support `areaSource:'space'|'custom'` and `areaSpaceId` (`finEnergyAreaSource` and native Ref `finEnergyAreaSpaceRef`). Space mode explicitly references an accessible native Site/Floor and reads its current area. Custom mode uses `area` / `finEnergyArea`; omitted source preserves a legacy custom number. Installation/coverage location never supplies an implicit service area. Ordinary energy reads do not require valid area metadata.

With `perArea:true`, reports freeze `extra.areaBasis:[{nodeId,categoryId,name?,basis,baseValue,baseUnit,value,unit,area:{value,quality,unit:'m²',sources:[{id,name,area,source}]}}]`. Same and contained service spaces count once; separate spaces sum. Multiple unknown custom boundaries return `ambiguousArea`; missing/invalid area returns `missingArea`. Base consumption remains available in areaBasis. Each energy category uses its own selected objects. `__selection__` identifies category totals; `difference` marks a leakage-report difference. Single-category `normalizationArea` retains its compatible value/quality/unit fields and adds sources. UI and exports use the frozen result.
POST `records/delete` body `{id,mod}` -> `{deleted:id}`. Reject referenced/occupied/cyclic/duplicate config.
POST `tree/copy` or `tree/move` body `{id,parentId,mod}` -> `{records:FinEnergyRecord[]}`.

POST `tree/manage` is admin-only. `action=save` accepts `{records:FinEnergyRecord[]}` (up to 200) and validates the entire final batch before a single Folio commit; new or changed physical bindings reject any existing meter binding to that point. For new trees, use `tree/manage` with `dimension:'space'|'metering'|'organization'`:

- `action:'move',items:[{id,mod}],parentId:string|null`: moving a meter changes only `spaceId`, `meterParentId`, or `organizationId`; moving a space/organization changes its same-kind parent. A null parent clears that dimension's relationship. Other dimensions and legacy placement remain intact.

The server saves settings on that target and clears the copied expression and canonical alias. For a non-meter configuration copy, the server allocates a new record, clears source/canonical bindings and excludes the copy from totals. Retained relationships are subject to validation.

Omitting `dimension` preserves legacy tree grouping. The original `tree/move` and `tree/toggle` routes retain their legacy relation semantics; use `tree/manage` for dimension-aware operations. Legacy `tree/copy` copies group hierarchies. Copied meter configurations clear physical/expression/canonical bindings and default to excluded-from-totals.
`action=previewDelete` accepts `{items:[{id,mod}]}` and returns `{revision,roots,records:[{id,kind,name}],blockers:[{id,kind,name,referencedIds}]}`. The complete FIN Energy subtree is selected; templates, expressions, COP or other outside configuration references block deletion. `action=delete` accepts the same items and preview revision; it rejects changed configuration and returns `{deleted:string[]}`. It deletes only FIN Energy configuration, retaining native points, equipment and histories. Alarm/job audit records follow the existing retained-event policy.

The engineering UI scopes direct children, descendants or all objects; paths follow the selected dimension's relationships, never name prefixes. Drag/drop and batch moves use the same validated backend. New physical meters default to included totals, sensors remain excluded, and reused meters retain their saved flags. The wizard suggests a category only when normalized unit and native-marker evidence agree uniquely; ambiguous batches require an explicit choice. Short aliases use explicit native naming metadata, with original names retained in provenance. Metering energy folders are presentation-only and cannot become report objects or relation targets. Desktop uses a right inspector and mobile uses a detail drawer. Advanced single-object fields are collapsed without discarding their saved values.

## Three-tree migration

This compatibility protocol applies when POST `migration` includes `target:'threeTree'`. Include the target on preview, apply and rollback. The default migration protocol is native-equipment migration described above. GET `migration/preview` uses that default. Both protocols require an administrator. POST `migration` with `{action:'preview',target:'threeTree'}` returns the three-tree plan below.

`{version:1,revision:string,sourceRevision:string,records:FinEnergyRecord[],suggestions:MigrationSuggestion[],warnings:string[],counts:{added,updated,canonicalAliases,spaces,suggestions,unboundMeters}}`.

`records` contains automatic additions and full edited records. `MigrationSuggestion` is `{id,type,title,reason,requiresConfirmation:true,records:FinEnergyRecord[],patches:object[],recordIds:string[],sourceIds:string[],count:number,placementRequired?:boolean,parentId?:string}`. Suggestion types include `legacySpace,nativeFloor,meterTopology,legacyGroup`. Full proposed records support review; field patches allow independent space and topology proposals to be combined without resetting each other's changes. A `placementRequired` suggestion contains no automatic placement and needs an explicitly selected target space.

POST `migration` with `{action:'apply',target:'threeTree',revision,sourceRevision,acceptedSuggestionIds?:string[],placements?:{[suggestionId]:spaceId}}` applies the automatic records plus accepted proposals and explicit placements. Both revision values must be copied unchanged from the preview. The server regenerates the plan and compares the FIN Energy configuration revision and native-source metadata signature; changes require a fresh preview and return HTTP 409 / `CONFLICT`. Unknown proposal IDs or invalid placement targets are rejected. A placement key must identify a `placementRequired` suggestion; its target must be an existing space or a new space included by an accepted proposal. Overlapping explicit placements must agree for each meter. The complete candidate is validated before one Folio commit. The response is `{applied:number,job:FinEnergyRecord|null}`; a no-op returns zero and no job.

Migration creates only assured site roots and source-backed placements automatically. Native `submeterOf` is carried over only when all supplied references map unambiguously to the same existing canonical upstream meter in the same energy category and do not introduce a cycle. Native floor names may be functional groups, so floor/building placement inferred from names remains a confirmation proposal. Functional groups such as `总能耗` (total energy use) and `风机盘管` (fan-coil units) require an explicit target. Groups with no meters remain unbound. The `1#楼水表` (Building 1 water meter) wrapper pattern can produce a batch topology proposal whose parent is the canonical record for the existing master point; sharing a group or a name never creates automatic topology.

Duplicate point aliases receive `canonicalId`; canonical selection prefers an included active total meter, otherwise a deterministic existing record, while retaining a consistent prior canonical choice. Incompatible categories/expressions produce warnings. Generated space IDs are deterministic qualified FIN refs, so re-preview after application does not create duplicate additions. Existing groups, meter `parentId`, original point bindings, and legacy total flags remain intact. Migration never writes native FIN point/equipment tags or source histories.

Applied migrations retain a `job` with `action:'treeMigration',status:'applied',migrationKey,processed`, plus retained `treeMigrationSnapshot` job records containing before/after FIN Energy configuration. POST `migration` with `{action:'rollback',target:'threeTree',jobId,mod}` requires the current migration-job mod and returns `{rolledBack:number,job:FinEnergyRecord}`. Rollback compares current business fields with the saved after-state, rejecting changed or missing migrated records with HTTP 409. It also validates the restored candidate and rejects deletion of migration-created objects that acquired external references. A successful rollback atomically restores prior records, removes migration-only additions, and marks the job `rolledBack`; audit/snapshot records remain retained. This is a FIN Energy configuration rollback, not a native-history backup.

### Comparison interval alignment (0.2.9)

`comparison` accepts `comparisonAlignment: "duration" | "calendarMonth"`. With `duration`, the two intervals must have the same duration. This mode supports hour/day/week and creates equal-length buckets from the start of each interval. With `calendarMonth`, both intervals must cover full calendar months and use `period=month`. The buckets reflect the actual number of days in each month. Requests that omit the parameter keep their original calendar buckets and date ranges. The frontend resolves `comparisonPreset` from the template. The backend uses the resolved `from/to/otherFrom/otherTo` values. The date picker includes the selected end day. The wire interval includes its start and excludes its end. The chart pairs buckets in sequence and preserves their original timestamps.

### Object comparison baseline (0.2.10)

A same-period comparison can specify `baselineId`, which must belong to `nodeIds`. Requests in any of the three dimensions normalize that reference using the same rules. The backend matches the baseline by object, energy category and unit. It returns `comparisonBaselineId/Name` and the `referenceId/Name`, `current/reference`, `difference`, `percentage` and `percentageQuality` fields in `comparisons`. Older templates may still carry `referenceIds`.

### Energy forecast (0.3.0)

For `kind: "forecast"`, use `metric: "energy" | "cost"` and `period: "day"`. Supply a training interval of 28–180 full days in the project time zone through `from/to`, with an exclusive end at or before the start of the current day. Select 1–10 meters or reporting scopes and set `forecastDays` to 7 (default), 14 or 30. `trainingDays` and `forecastRolling` capture template intent in the frontend. The server uses the resolved dates. Source history is read-only. The calculation excludes samples beyond the training cutoff. It can use a cumulative reading exactly at the cutoff as a boundary reading.

Cost forecasts fit the complete daily costs of each canonical meter independently, then combine forecasts for the same set of members. The model is labeled `meterSum`. Space and organization affect grouping only. `summary.forecastTotals` gives the deduplicated cost forecast and `extra.forecastMeterIds` identifies its members. `forecastBasis:historicalMeterCostPatterns` identifies an estimate based on historical cost patterns. The forecast excludes future tariff changes and has no billing status. The reference error half-width sums the members' error bands. Combined backtests use the historical holdout samples shared by the members. Cost forecasts have no area normalization.

The model needs at least 28 usable days, 80% completeness, three usable days for each weekday and complete data for the last seven days. Depending on the forecast length, it holds out up to four non-overlapping rolling backtest windows, each trained only on preceding history. It compares the same weekday in the previous week, a weighted mean for recent matching weekdays, and a weekly trend with decaying weights. Selection uses MAE and requires an improvement greater than 2% before choosing a more complex model. A 30-day forecast needs at least 44 calendar days to form one backtest. WAPE is null when total actual usage is zero. Model selection and evaluation use the same historical holdouts. The reported errors describe those holdouts.

Series add `role: "history" | "forecast"`. Forecast points have quality `predicted` and include `lower/upper`. Detail rows add `phase/model`. `extra.forecasts` returns forecast totals, model, MAE, WAPE, baseline MAE, sample coverage, status and simulated-source markers for each object. `extra.backtests/modelScores` retain backtest evidence. The daily reference band uses the 90th percentile of the selected model's absolute backtest errors. Future coverage may differ. If data is insufficient, the report retains history and states why no forecast series is available. Forecasts use history without weather or operating schedules. Each object is forecast separately, and parent meters and submeters must be kept distinct when reporting totals. The chart, table and exports use the same result. The legacy `regression` endpoint behavior, links and templates remain compatible.

### History cleaning (0.10.0)

`records` and `records/delete` support `kind:"cleaningProfile"`. Fields include `name`, `mode:"drop"|"replace"|"rollover"`, `parameters` and `version`. A change includes the previous `mod/version`. The general initial parameters are `{deltaMin:0,timeMax:"1h",defNull:true}`, with no default maximum increment. Clearing an optional parameter removes its rule. A number with a unit is represented by `{type:"number",value:0,unit:"kWh"}`. `defVal` must be an explicit typed number or `{type:"na"}` for a Haystack NA. Set the numeric rollover modulus to the number of counter states, such as 32768 for a counter spanning 0 through 32767. Rollover also requires a valid positive increment or rate limit.

Excluding a device or disabling cleaning restores only settings owned by this module. A profile update and its referencing point updates share one optimistic Folio commit.

The built-in `finEnergyCleanHis(rec,dates,opts,yield,config:{})` function and reports share the reader for the primary point's own raw history. A new query applies the current saved, validated cleaning profile, with precedence given to explicit parameter overrides. Disabling cleaning stops the previous profile from applying. An external history function retains its own output convention. An unrecognized function must explicitly declare cumulative or interval mode. Existing report snapshots and exports stay frozen. An explicit preview applies the proposed configuration without writing history. Ordinary queries read the selected device's primary point history directly. Old usage batches, auxiliary archives, current submeter sums and formula-input histories cannot substitute for it.

POST `cleaning/preview` accepts `{nodeId,from,to}` and optionally explicit `pointId/profileId/profile`. Read-only users can call it. The range must be greater than zero and at most 31 days. It returns `raw/cleaned/details/summary/profileSnapshot` without modifying history. `valueType:"number"|"null"|"na"` distinguishes zero, missing values and NA. Diagnostic details record the raw value, previous value, duration, rule trigger and replacement marker.

`extra.cleaning` retains the profile ID, version, full parameters, source, filter/replacement/NA counts and coverage. `filtered` usage is a usable subtotal. `substituted` usage includes replacements. NA propagates as `value:null,valueType:"na",quality:"na"`. An incomplete subtotal can feed clearly labeled observed-usage means, peaks and shares. Whole-range metrics, COP, differences and tiered tariffs continue to check completeness. Recalculation preserves the original measurement quality. Report diagnostics include up to 1000 anomaly details and return `detailsTruncated`. Previews retain diagnostics for the range read. Existing exports retain the parameters and results captured at generation time.

### Historical record — 0.11.x object archives and effective relationships

This section preserves the old contract to identify historical evidence and records. Reporting has interpreted relationships from the current configuration since 0.12.0. Auxiliary usage archiving and recalculation stopped in 0.12.9. The following old generation, publication and historical correction paths describe retired behavior.

In 0.11.1, the server injected effective-date snapshots for historical relationship segments in the production `leak/energyFlow` report path and rejected client-supplied versions of that evidence. Energy flow used common interval boundaries in each meter's own history to distinguish complete periods, missing or anomalous periods, and an unpublished tail. Collection intervals could differ without matching every timestamp. Incomplete intervals were not prorated and gaps remained missing. Native meters and legacy records pointing to the same source were deduplicated using the binding stored in the historical snapshot. Past relationships came from historical configuration.

From 0.11.2, the default overview showed the full query window and preserved the original `from/to`. The longest complete subperiod no longer stood in for a full week. `extra.energyFlowOverview:{from,to,unknownTopologySeconds,rows}` and top-level `rows` listed each meter's history individually, with master and submeter totals kept separate. Each row provided `value/quality/valueType/complete/coverage/activeSeconds/coveredSeconds/removed/sourceIds/periods`. Coverage was duration-based. Only intervals wholly contained in the query and effective window contributed usage. ### Native FIN alarms (0.8.3)

### Important changes in the Message Center

GET `messages/changes?offset=0&limit=30` returns `{items:ChangeMessage[],total,offset,limit}`. `offset` is a nonnegative integer. `limit` is 1–200 and defaults to 30. An invalid range returns 400. Responses use the existing `{ok:true,data:...}` envelope. This read-only endpoint observes current change messages. Acknowledgment, recalculation and configuration or log writes use their own behavior. Existing `alarms` and `alarms/ack` behavior is unchanged.

`ChangeMessage` has shape `{id,ts,action,category,objectId,objectName,objectKind,actor?,changes:[{field,before,after}],detailsRestricted?}`. `action` is `created|updated|deleted`. `category` is `relationship|source|configuration`. Each object epoch emits at most one message. For changes covering several field types, the category priority is relationship, then source, then configuration. Results sort newest first, with the epoch sequence and immutable epoch ID breaking timestamp ties. The server counts the total after applying access filters. New commits during pagination can shift the offsets.

Messages project adjacent before-and-after configurations from existing `finEnergyMeterEpoch` records. Coverage includes tracked meters, sensors, categories, end uses, expressions, cleaning profiles, organizations and spaces. Initialization snapshots, identical values and edits confined to sensitive or non-material fields do not generate messages. New commits record the current FIN username in a separate `finEnergyEpochActor` tag. Older logs without an actor omit `actor`. Actor and initialization markers remain outside the configuration used for calculation.

The allowlist contains current ownership references, primary-point and formula bindings, expressions and variables, names and kinds, `autoSum`, `includeInTotals`, `historyMode`, `maximum`, `unit`, cleaning enablement, profile and mode, supported `parameters`, and alarm enablement and thresholds. `parameters` includes only existing cleaning parameter names and supported numeric or unit-bearing values. `alarmLimits` contains only `categoryId` and `limit`. Passwords, tokens, credentials and complete previous configurations stay outside the projection.

Current object access controls message visibility. Logs for currently deleted objects are visible only to administrators. The server checks historical references against current permissions, including previous parent references, expression `variables` and references in `alarmLimits`. If a nested reference is invalid, unreadable or unsupported, the entire field is omitted and the response sets `detailsRestricted:true`, protecting its reference IDs, cached names and partial old values. A corrupt epoch produces only a generic server warning. The unknown preceding value does not become a creation or a known change. The next valid snapshot establishes a new comparison baseline. Reporting, meter selection and virtual-meter calculation run independently of this message projection.
