# EnerCubix Constitution

## Core Principles

### I. 以现有项目和已确认需求为准

遵循用户当前指令、AGENTS.md 和 docs/team/README.md。复用已有需求、设计、接口及测试；只修改完成本次目标所需范围。保留 FIN Folio、历史服务、原生身份和权限边界，不借开发工具接入改造业务架构。

### II. 明确结果，连续交付

每项任务有单一交付负责人、修改范围、依赖和可执行验收。大功能使用聚焦的 spec.md、plan.md、tasks.md，已有内容通过链接引用。需求已确认就连续实现；小修复、文案和局部样式沿用短流程。路径和常规实现细节由经理决定，重要业务歧义才向用户询问。

### III. 业务数据与统计语义保持一致

普通查询只读，不改写原始历史。相同最终去重表计集合、起止范围、数据截止、指标／单位、清洗和计量配置应采用相同基础用量与汇总语义；视角只改变选择、分组和展示。缺测、NA、真实零和替代值分别解释，费用、COP、损耗等结论保留各自必要条件。

### IV. 中英文与业务原文

所有新增界面、日期控件、图表、提示、校验、导出和无障碍文案接入现有 i18n 入口，覆盖中文、英文及适用的手机布局，保留扩展法文的路径。设备名称、项目名称和用户业务数据保持原文。

### V. 证据决定完成

缺陷尽可能先复现再最小修复。执行直接相关测试、类型检查、构建和适用的运行验收；低影响文档或格式改动不新增镜像式测试。区分源码检查、离线计算、受控浏览器、隔离 FIN 和目标现场 FIN。遇到失败先定位、修复并继续；证据不足时准确说明限制，不以任务勾选或文档齐全代替功能交付。

### VI. 并行隔离与统一发布

最多两个实现任务并行；每个并行实现使用独立工作区和功能目录，不争用 .specify/feature.json。公共文件、SDK、候选包、版本和共享 FIN 实例由指定负责人协调。发布时统一 Pod、根 package、前端 package 与锁文件版本，冻结源码证据和包哈希，按对应授权部署及核验。

## Workflow

默认功能目录为 specs/<看板任务ID>-<简短名称>/，经理在调用 Spec Kit 时提供该目录和已有确认，不把目录选择转交给用户。看板是唯一排期入口，tasks.md 记录功能内部执行，两个层级链接而不重复维护状态。原型、已有测试记录及回放不能升级表述为当前生产证据。

普通改动由当前负责人自检并核对证据；仅用户明确要求或高风险变更时增加独立审查，不在每个小步骤派审查代理。没有新改动或新问题，不重复全量检查。新建聊天、跨聊天发指令、代理编排、远端写入及生产操作继续遵循当前用户和工具的授权要求。

## Governance

本文件承接项目现有约定，用户当前指令优先；Spec Kit 默认提示不得新增与之冲突的重复确认或审批。保持最小、可运行、可验证的增量。工具升级不覆盖这些项目规则；需要改变重要业务规则时单独提出具体取舍。
