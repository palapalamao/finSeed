# EnerCubix 开发团队与交付流程

版本：工作方式 V1，2026-10-25。适用：用户作为产品负责人，多个人或 AI 聊天协作开发同一产品。

目标：你能随时看清谁负责什么、下一步做什么、哪里卡住、哪些结果已验证。每轮交付可运行的小增量，减少等待、重复开发和代码相互覆盖。

入口：[任务看板](board.md) · [派工与交接模板](templates.md) · [Spec Kit 使用方式](spec-kit.md) · [提交说明](../../CONTRIBUTING.md)。

## 1. 选用的工作方式

采用短周期目标、拉式看板、短分支和按风险验证。这是适合当前规模的组合流程，借鉴敏捷原则，不宣称完整实施 Scrum。

| 选择 | 收益 | 成本与适用性 |
| --- | --- | --- |
| 短周期看板＋GitHub Flow，当前采用 | 任务可见、优先收尾、容易插入缺陷修复 | 经理需维护负责人、边界与状态 |
| 完整 Scrum | 固定事件和角色，适合稳定的多人产品团队 | 当前多个 AI 聊天协作不需要完整会议安排 |
| 全面引入 AI 编排或规范生成框架 | 可复用自动拆解与执行机制 | 增加维护与流程成本，先吸收模板和任务追溯做法 |

先运行两个交付周期，再根据等待时间、返工和逃逸缺陷调整。不要以聊天数量、代码行数或文档数量衡量产出。

## 2. 团队分工

角色是职责，可以由同一个人或聊天兼任；不是要求常驻同等数量的代理。

| 角色 | 当前承接方式 | 对交付负责 |
| --- | --- | --- |
| 产品负责人 | 用户 | 目标、优先顺序、业务规则和重大范围取舍；只需确认有实质分歧的事项 |
| 团队经理／集成负责人 | 本聊天 | 唯一任务队列、拆分与依赖、归属与冲突协调、集成顺序、质量证据和交付汇总 |
| 产品／业务分析 | 现有产品经理及业务检查聊天，按需参与 | 把需求转成场景和验收条件，复用已确认设计，避免重复设计 |
| 开发负责人 | 现有“开发”聊天；独立界面任务可另设一位负责人 | 端到端实现、自测、最小变更和可验收候选；每任务仅一位交付负责人 |
| 测试负责人 | 现有“测试”聊天，候选就绪后执行 | 根据验收条件复现与验证，独立核对关键数值和边界，报告通过范围与限制 |
| 发布负责人 | 团队经理协调，由一位指定执行者承接 | 统一版本、冻结包和源码证据、发布及回滚；不允许多个聊天同时打包或重启同一实例 |

架构、设计和安全审查按需要加入。普通低风险改动由开发自检、经理核对验收证据；用户明确要求或涉及高风险变更时才启用独立审查。测试可独立验证，不要求每个小步骤启动新的代理。

当前聊天角色映射用于协作设计；新建聊天、给其他聊天发指令、安装服务及生产操作继续遵循当前工具和用户授权边界。没有后台运行的经理或监控服务。

## 3. 唯一任务队列

当前以 [board.md](board.md) 为唯一排期记录；需求、设计、测试记录和聊天都是证据来源，不另维护第二份完成状态。

后续启用 GitHub Issues／Projects 后，每个任务对应一个 Issue，看板显示这些 Issue；本地看板只保留入口和历史快照，停止手工维护双份状态。聊天是执行场所，不能仅凭聊天显示“空闲”或“正在运行”判断任务完成。

任务最少记录：目标、优先级、单一交付负责人、状态、范围、依赖、验收方法、最新证据和下一步。阻塞是任务的附加标记，必须写明原因、等待谁、解锁条件和下一次行动；不能仅写“卡住”。

优先级：P0 为数据／权限风险或核心流程阻断，P1 为当前周期的重要任务，P2 为后续增强。产品文档的“首期 P0／后续 P1”是功能分期，不能直接当作缺陷优先级。

## 4. 流转和完成条件

```mermaid
flowchart LR
  A[待梳理] --> B[待开发]
  B --> C[开发中]
  C --> D[待验收]
  D -->|未通过| C
  D -->|通过并集成| E[已完成]
  E --> F[按发布计划交付]
```

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| 待梳理 | 想法、缺陷或改进进入队列 | 明确价值、范围、验收、负责人和依赖；重要歧义已解决 |
| 待开发 | 需求已具备执行条件 | 有可用容量和独立工作区，负责人开始执行 |
| 开发中 | 已建立基线并开始实现 | 自测通过，交付不可变候选、改动范围和证据 |
| 待验收 | 测试能复现候选及其配置 | 验收与相关回归通过，完成必要的集成检查 |
| 已完成 | 代码任务已验收并纳入约定的集成基线；研究／文档任务按相应产物验收 | 发布需求另按发布状态追踪 |

发布状态单独记录“未纳入／候选／已冻结／已发布”，以及版本、包哈希、环境和证据。合并不等于上线，冻结包也不等于部署成功。

开发就绪条件（DoR）：

- 一个可观察的用户结果，明确不做的内容；有已确认设计就直接使用。
- 验收可执行：输入、操作和预期明确；缺陷尽可能有稳定复现。
- 单一交付负责人，依赖和共享文件归属明确。
- 风险、需要的验证环境和已授权操作已知。

代码完成条件（DoD）：

- 请求行为可运行，缺陷有修复前后证据；相关旧行为保持正确。
- 相关测试、类型检查、构建和必要运行验收通过；不适用项说明理由。
- 适用的中英文、日期、图表、导出、无障碍文案和手机布局已核对。
- 每项关键证据对应同一提交或源码清单及候选包；候选改变后，受影响证据需更新。
- 没有混入无关文件、业务原始数据或认证材料；剩余风险与限制明确。

## 5. 控制同时开展的工作

初始限制：最多两个实现任务同时进行；每位开发一次主攻一个任务；最多一个共享 FIN 验收／发布候选占用测试实例。发现冲突时先收尾或解除依赖，再拉取新任务。

每项任务优先拆成一个可独立验收、集成和回滚的小增量。通常以半天至两个工作日的人工可验收范围为拆分参考，复杂任务继续按业务结果拆分；这是粒度建议，不是 AI 的工期承诺或行数指标。

拆驾驶舱时，先完成“一个真实站点、一个能源、一个时间范围的指标卡和下钻”，再扩展六个视角与汇报。不要同时独立开发整套前端、后端和数据模型后才第一次集成。

优先处理待验收、阻塞和返工。测试在开发时先准备固定输入和预期，不必等所有代码写完才开始理解需求。

## 6. 并行开发和代码集成

- 新任务使用独立 Git worktree／分支，分支默认 `codex/<任务ID>-<简短名称>`；优先复用合适的现有工作区，不为只读研究新建工作区。
- 不在其他任务正在使用的工作区切分支、重新安装依赖或覆盖构建输出。端口、临时目录、SDK 副本和验收实例也要分配归属。
- 一个文件在同一时段只有一个集成负责人。涉及 `ReportWorkspace.tsx`、`ReportView.tsx`、`types.ts`、后端报告引擎等公共位置时，先约定最小接口与合入顺序；不同工作区仍可能产生冲突。
- 版本号、锁文件、公共翻译词库、发布包和 FIN 重启由指定负责人协调。开发者提交功能需要的词条，但不能并行重写整份词库或各自升版发布。
- 每个 PR 只解决一个问题，带相关测试与关联任务；重命名、重构和功能修改按可理解边界拆开。不要为了缩小行数把测试移到无关任务。
- 候选集成后跑受影响的检查。没有新改动或新问题，不重复同一轮全量验证；风格建议不阻止正确、安全且符合需求的交付。

当前共享工作区已有大量未提交和并行改动。过渡时让现有任务按既定归属收尾，先盘点与保存可恢复材料，再按明确归属分批集成；不整体暂存、不重置、不强推、不自动搬走或删除业务文件。新任务再切换为独立工作区。

## 7. 按风险验证

| 改动 | 最小验证 | 额外要求 |
| --- | --- | --- |
| 说明、文本、低风险样式 | 内容、链接或可见效果检查；适用的类型／构建检查 | 不为格式变更新增镜像式测试或独立审查代理 |
| 普通功能／缺陷 | 可执行验收、受影响单测、类型检查、构建、相关浏览器场景 | 中英文与手机按影响范围覆盖 |
| 统计、清洗、总分表、历史关系 | 固定输入的独立期望、前后复现、隔离 FIN 集成 | 同范围、截止、配置和最终去重表计集合核对跨视角数值；NA、缺测与真实零分开 |
| 身份、权限、迁移、部署或不可逆行为 | 对应权限／数据完整性／回滚检查与适用的独立复核 | 使用现有授权与受控流程，不能以 CI 通过替代专项证据 |

验证层级分别记录：源码检查、离线计算、受控数据浏览器、隔离 FIN、目标现场 FIN。演示原型、历史验收报告和回放结果不能升级表述为当前生产验证。

原始历史不被普通查询改写，统计口径不随展示视角改变。完整区间结论、已有用量和质量覆盖分别解释，费用、COP 和损耗保留各自可比性条件。

## 8. 已准备的自动检查

`.github/workflows/quality.yml` 在 PR、main 推送或手动触发时执行：

1. `Source quality`：版本检查器测试、Pod／根／前端／锁文件版本一致性、锁定依赖安装、前端单测、类型检查和构建。
2. `UI smoke (controlled data)`：Windows Edge 的既有多语言、手机和导出场景，保留浏览器证据七天。

工具版本固定到已核对的官方 Action 提交。流程兼容当前 `enerCubix.pod` 与仓库旧提交的 `finSeed.pod` 目录；二者同时存在时报错，避免默默选错源码。

上述文件在本地准备后，只有随代码提交并推送到 GitHub 才会运行。Issue 表单需要进入默认分支才出现在创建入口。当前没有创建远端 Project，也没有启用分支保护；本地检查通过不代表远端 CI 已运行。

本轮安装验证发现既有阻塞：已提交基线与当前锁文件均锁定 `tinyglobby 0.2.27`，独立 `npm ci` 请求其归档返回 404；当前工作区实际安装的是 `0.2.17`。已列入看板 N00。这里保留严格的锁定安装检查，不用旧 node_modules 或更改安装方式掩盖失败；其来源及兼容修复由锁文件负责人继续处理。

远端启用时，在首次成功运行后，把上述两个检查设为 main 合并的必需检查，要求最新候选检查通过；按实际人员配置合并权限。当前只有一个 GitHub 维护者时，不强制其给自己的 PR 提供另一份无法获得的账号批准，测试聊天的证据也不冒充另一位 GitHub 用户的审批。

GitHub 托管检查不安装或运行商业 FIN SDK，不读取生产凭据，不部署。后端与发布候选仍沿用已有 `scripts/test.ps1`、`scripts/acceptance.ps1` 和隔离 FIN 审计验收；发布负责人核对这些证据后才可交付。后续若增加专用运行器，应独立配置 SDK、许可和隔离网络，并限制受信任代码触发。

## 9. 发布与日常节奏

每个交付周期建议一周，仅选一个主要目标和少量可验收任务。紧急缺陷可打断，但经理必须写明换下的任务和影响，不能无限追加范围。

- 周期开始：经理给出目标、优先顺序、负责人、依赖及预计交付切片；用户只决定业务取舍。
- 工作中：状态变更、遇到阻塞、交付候选时更新看板；用户查看进展时，经理先刷新证据。默认不安排自动消息或重复日报。
- 周期结束：演示可运行结果，明确通过、未通过、待发布；复盘只选一项最影响效率的问题，并在下一周期改进。

发布时由一人统一升版，确认 Pod／根／前端／锁文件以及包内元数据一致，冻结源码清单和包 SHA-256；测试只针对该候选。包改变后重新判断受影响验证，不能让测试验 A、发布装 B。按环境既有授权安排部署、备份、回滚与安装后核验。

经理汇报固定回答：本期目标、谁在做什么、已验证结果、阻塞与等待、下一步、需要用户决定的事项。没有需要决策的事项就连续推进，不逐项确认实现细节。

首两周只记录四项：任务从开始到验收的耗时、等待验收时间、验收退回次数、发布后发现的缺陷。先建立真实基线，不编造达成率，不给 AI 套用代码行数或聊天数目标。

## 10. 分阶段采用

- [x] 准备团队职责、流转规则、任务／PR 表单、交接模板与版本检查。
- [x] 以现有任务建立初始本地队列，区分已在执行、待验收与候选规划。
- [ ] 当前在途任务收尾后，按归属整理待集成变更，下一项开发采用独立工作区。
- [ ] 按用户的远端发布安排提交流程文件，执行首次 GitHub CI，再启用必需检查与远端看板。
- [ ] 试行两个周期，基于等待与返工数据调整并发上限和任务粒度。

## 11. 调研来源和采用边界

核对日期：2026-10-25。以下是公开的一手流程，不以星标数证明效率，也不承诺采用后必然提高多少速度。规则为结合当前项目做出的取舍。

| 来源 | 采用的做法 | 在本项目的调整 |
| --- | --- | --- |
| [microsoft/vscode Development Process](https://github.com/microsoft/vscode/wiki/Development-Process) | 路线图、迭代目标、完成标准、集中测试与候选验证 | 其页面标注最后编辑于 2021 年；借鉴公开结构，不断言是团队今天完整内部流程；将其月节奏缩为试行的一周目标 |
| [google/eng-practices Small CLs](https://github.com/google/eng-practices/blob/0501c55016c0ef06308d0147700a895be28e5c45/review/developer/small-cls.md) | 一个自包含改动、关联测试、容易复核和回滚 | 按业务结果拆任务，不设置硬性代码行数门槛 |
| [google/eng-practices Review standard](https://github.com/google/eng-practices/blob/081822f3999b33c59277ad7d1c3360d027492850/review/reviewer/standard.md) | 用事实判断，兼顾改进与交付，区分必要问题和可选润色 | 普通任务自检与证据核对，高风险才增加独立审查 |
| [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) | 短分支、PR、检查、合并与可恢复历史 | 多聊天写代码使用隔离工作区，发布另设证据与权限边界 |
| [github/spec-kit v1.2.3](https://github.com/github/spec-kit/tree/v1.2.3) | 需求、计划、任务、实现可追溯 | 已接入项目内 Codex 技能及官方 Lean 预设；按需用于较大功能，小修复保留短流程 |
| [Scrum Guide 2020](https://scrumguides.org/scrum-guide.html) | 单一优先队列、透明进展、可用增量和共同完成标准 | 借鉴理念，保留适合 AI 协作的轻量节奏 |

实施参考：[GitHub Node.js CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)、[Issue 表单语法](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)。
